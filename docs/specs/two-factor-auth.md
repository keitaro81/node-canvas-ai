# 2 段階認証（v1.0・2026-11-14）

状態: **実装済み・マイグレーション 0023 適用済み・2026-11-14 デプロイ**。残りの手順（セッションの期限・運営の有効化）は §8。

## 1. 要点

- **方式は認証アプリ（TOTP）**。Supabase Auth 標準の MFA を使う。追加費用なし。
- **強制はサーバー側**。DB は RLS の restrictive ポリシー、Edge Functions は共通の確認。画面だけの制御ではない（パスワードが漏れて API を直接叩かれても通らないようにするのが目的）。
- **対象は 3 層**: ①各ユーザーが自分で有効にできる（任意）②チームのオーナーが「このチームは必須」にできる ③運営コンソール（/admin）は常に必須。
- **端末をなくしたとき**は、予備の認証アプリ（1 人 10 個まで）と、オーナー / 運営によるリセット。
- **今の利用者は何も変わらない**: 自分で有効にするか、チームが必須にするまで。

## 2. 決定（2026-11-14・ユーザー）

| 項目 | 決定 |
|---|---|
| 方式 | 認証アプリ（TOTP） |
| 対象 | 任意 ＋ チームのオーナーが必須にできる |
| Google でログインする人 | 必須のチームでは Google の人にも求める（規則は 1 つ） |
| 端末をなくしたとき | 予備の認証アプリ ＋ オーナー / 運営のリセットで始める（リカバリーコードは入れない） |
| 出し方 | 任意とチーム必須を一度に出す |
| セッションの期限 | 最長 30 日でログインし直し（Supabase のダッシュボードの設定・ユーザーが行う） |

## 3. 調べたこと（Supabase Auth・2026-11 時点）

| 項目 | 状況 |
|---|---|
| 認証アプリ（TOTP） | 無料。全プロジェクトで既定で有効。コードは 30 秒ごと・前後 1 区間のずれを許容 |
| SMS / WhatsApp | 有料アドオン（$75/月〜）＋ 送信料。SIM スワップに弱い → 採用しない |
| WebAuthn を 2 段階目に | ホスト版では提供されていない |
| パスキー | ベータ（supabase-js 2.105 以降。いまは 2.100.1）→ 将来の選択肢 |
| リカバリーコード | 非対応。代わりに要素を複数登録できる（上限 10） |
| 試行回数の制限 | IP ごとに 15 回/分（変更不可）。ユーザー単位でロックするフックは Team / Enterprise プランだけ |

保証レベル（AAL）: JWT の `aal` が `aal1`（パスワードや Google でログインしただけ）か `aal2`（2 段階目も通した）。同じ端末では、トークンを更新しても `aal2` のまま（ログアウトするまで再入力は要らない）。

実機で確かめた Auth サーバーの挙動:

- 要素の検証に成功すると、そのユーザーの **aal2 未満の他のセッションは無効になる**（他の端末はログインし直し → コード入力）。
- 検証済みの要素があるユーザーは、aal2 でないと **要素の追加・削除、パスワード / メールの変更ができない**（`insufficient_aal`）。パスワードを盗んだだけでは 2 段階目を外せない。
- 要素を消すと、**その要素で通したセッションは aal1 に戻る**（本人の削除でも、オーナー / 運営のリセットでも）。認証アプリが 2 つある人が「いまのログインで使った方」を消すと、その場で残りの方のコード入力になる。
- supabase-js は、コード入力の直後のトークンを **Realtime には渡さない**（渡すのは SIGNED_IN と TOKEN_REFRESHED だけ）。そのままだと最長 1 時間、変更通知が RLS で止まるので、`authStore` が `MFA_CHALLENGE_VERIFIED` で `realtime.setAuth` を呼ぶ。

## 4. 判定の規則（1 つだけ）

> **2 段階目が必要** ＝ 本人が検証済みの要素を持っている、**または** 所属チームが必須にしている。
> 必要なのに `aal2` でないセッションは、データに触れない。

同じ規則を 3 か所で判定する（純関数 `src/lib/auth/mfaGate.ts` の `mfaGateOf` を画面と Edge で共用。DB は同じ内容の SQL）。

| 場所 | 実装 |
|---|---|
| DB（`migrations/0023_mfa.sql`） | `public.mfa_satisfied()`（security definer）＋ RLS が有効な全テーブルと `storage.objects` に restrictive ポリシー `mfa_gate`。既存のポリシーは変えない。RLS を通らない RPC（確認結果・出力の記録・レイアウト保存・編集ロック・本日の利用数・ライブラリの最終利用）には本体に同じ条件 |
| Edge Functions（`api/_auth.ts`） | `mfaBlock()` を、JWT を検証した直後に全入口（fal proxy / batch / storage 3 つ / team）で呼ぶ。満たさなければ 403 ＋ `code: 'mfa_required'` ＋ `gate`（`challenge` か `enroll`）。チームの必須フラグは RPC `team_requires_mfa`（人ごとに 30 秒キャッシュ）。dev のミドルウェア（`vite.config.ts`）も同じ |
| 画面（`AuthGuard` ＋ `mfaStore`） | ログイン済みで 2 段階目が要るときは、コード入力（`MfaChallengeScreen`）か登録（`MfaEnrollScreen`）だけを出す |

- 要素を持たず、チームも必須でないユーザーは `mfa_satisfied()` が常に true。service role（Edge・cron）と未ログインも true。
- ポリシーは `(select public.mfa_satisfied())` の形なので、行ごとではなく文ごとに 1 回だけ評価される。判定用の `can_view_batch_job` / `can_edit_workflow` は行ごとに呼ばれるので変えていない。
- 画面が「必須か」を知るための RPC `public.mfa_status()`（aal1 のままでも呼べる）。
- 運営コンソール（`api/admin/_adminLogic.ts`）は、運営であることに加えて **aal2 を必ず求める**（他人のアカウントを作り、2 段階認証を外せる面なので）。
- チームの必須の切り替えとメンバーのリセット（`api/team/_teamLogic.ts`）は、**オーナー本人が aal2** のときだけ。パスワードだけを盗んだオーナーのアカウントからは、必須を外すことも、メンバーの登録を消すこともできない。
- リセットと必須の切り替えは `public.mfa_events` に記録する（service role だけが読み書き）。

## 5. 画面

1. **ログイン後のコード入力**: パスワードでも Google でも、認証アプリを登録済みなら 6 桁のコードを求める。複数あれば選べる。
2. **Account の「2 段階認証」**（`MfaSettingsSection`）: 「有効にする」→ QR コード（読めなければキーを表示）→ 6 桁で確認 → 有効。予備の追加・削除。チームが必須のとき、最後の 1 つは消せない。
3. **必須のチームで未登録の人**: ログイン後に登録の画面だけが出る。招待リンクから入った新しいメンバーも同じ（参加した直後に登録の画面に替わる。登録が済むと招待リンクのページに戻り「参加しました」と出る — 参加が済んだ印を `src/lib/team/joinDone.ts` がタブの間・10 分だけ覚えている）。招待リンクのページ（/join/:token）は、判定を待つ間も出したままにする（その場でアカウントを作った直後の「参加しました」を消さないため）。
4. **チーム設定**: オーナーに「このチームで必須にする / 必須を解除する」。メンバー一覧に登録の有無と「2 段階認証をリセット」。オーナー自身が 2 段階認証を済ませていないと押せない。
5. **運営コンソール**: メールアドレスを指定してリセット。2 段階認証を済ませていない運営には「2 段階認証が必要です」と Account への案内を出す。
6. **パスワードの再設定**: リセットメール → コード入力 → 新しいパスワード。メールを乗っ取られても 2 段階目は外れない。

画面の判定（`mfaStore`）は表示を速くするための工夫をしている: 認証アプリを登録済みならサーバーの答えを待たずにコード入力を出す／「チームが必須か」は端末に覚えておく／サーバーの答えは 8 秒で打ち切って手元の値で決める（読み込み中のまま止めない）。どれも表示だけの話で、値を書き換えてもサーバー側の強制は変わらない。

## 6. 端末をなくしたとき

| 手段 | 内容 |
|---|---|
| 予備の認証アプリ | 登録後に「別の端末やアプリにも登録」を勧める |
| オーナーによるリセット | チーム設定のメンバー一覧から。同じチームのメンバーだけ・自分自身は不可・オーナーが aal2 であること |
| 運営によるリセット | /admin から、メールアドレスを指定。オーナーが全員なくした場合など。本人確認は運用で |
| 運営本人がなくした | 別の運営がリセットするか、Supabase の SQL Editor で `delete from auth.mfa_factors where user_id = '…'`（0023 の末尾 C） |

リセット後は「登録なし」に戻る。チームが必須なら、次に開いたときに登録し直しになる。

## 7. 影響と注意

- **運営コンソール**: デプロイ後は、運営ご本人が Account で 2 段階認証を有効にするまで /admin を開けない。
- **チームで必須にした直後**: サーバー側はすぐ効く（DB は即時・Edge は最長 30 秒）。未登録のメンバーが作業中だと、その場から保存や生成が通らなくなる（保存前の変更が失われることがある）。切り替えの確認文でそう伝えている。先にメンバーへ知らせてから切り替える。
- **必須にしても、未登録の間は守られていない**: 未登録のメンバーのパスワードが先に漏れていた場合、その人になりすまして認証アプリを登録できてしまう（「最初のログインで登録」の方式に共通の限界）。必須にしたら、チーム設定のメンバー一覧で全員が登録済みになったことを確かめる。登録済みになった後は、パスワードだけでは認証アプリの追加・削除もパスワードの変更もできない（実機で確認: いずれも `insufficient_aal`）。
- **他の端末**: 有効にした時点で、ほかの端末（ほかのブラウザ）はログインし直しになる。同じブラウザの別のタブはそのまま使える。
- **総当たり**: 6 桁 × IP ごと 15 回/分。ユーザー単位のロックは Pro プランでは掛けられない。パスワードを破られた上での話なので受け入れる。
- **発行済みの署名 URL**（画像・動画）は期限まで有効（URL を持っていれば見える。新しくは発行されない）。
- **本番の Basic 認証**はサイト全体の入口で、利用者ごとの認証とは別。
- **テスト用・デモ用アカウント**: 認証アプリを登録しない限り影響なし。

## 8. 出す手順

1. **マイグレーション 0023**（ユーザー・SQL Editor）: staging → 本番の順に、ファイル全体を 1 回で実行。途中の自己確認に失敗したら全体が取り消される。適用後、ファイル末尾の確認クエリ。適用しただけでは誰も止まらない。
2. **デプロイ**（コード）。順序は「マイグレーション → コード」。コードは 0023 が無い環境でも落ちない（チームの必須の欄とメンバーの状態を出さないだけ。個人の 2 段階認証は動くが、DB 側の強制が無い）。
3. **セッションの期限**（ユーザー・Supabase ダッシュボード）: Authentication → Sessions →「Time-box user sessions」を 30 日に。
4. **運営ご本人**が Account で 2 段階認証を有効にする（予備も登録しておく）。

戻し方（0023 の末尾）: DB 側の強制をすべて止めるには `mfa_satisfied()` を「常に true」に置き換える 1 文。チームの必須だけ外す・特定の人の登録を消す SQL も同じ場所にある。
